# M3 — Temporal jitter + contact details

Ordered checklist; spec references are to `SPECIFICATION.md`. Package root:
`io.github.dconneely.alterego`.

- [ ] **1. `AlterEgo.DateField`, `AlterEgo.TimeField`, `JitterOptions<T>`**
  - `AlterEgo.DateField { MONTH, YEAR }` and `AlterEgo.TimeField { HOUR }` — nested enums on
    `AlterEgo` (alongside `AlterEgo.Builder`), selecting which date/time strategy a
    `shiftDate`/`shiftDateTime` call runs (spec section 4.5). Two separate enums, not one shared
    one, so an invalid combination (e.g. `HOUR` where a date strategy is expected) is a compile
    error, not a runtime check.
  - `JitterOptions<T>` — immutable value type, `T` is `LocalDate` or `LocalDateTime`. Three static
    factories: `min(T)`, `max(T)`, `minmax(T, T)`. No builder, no "unbounded" instance — an
    unclamped call simply omits the trailing `JitterOptions` argument.
  - Acceptance: all three types compile with full Javadoc; `JitterOptions` has no mutating
    methods.

- [ ] **2. `shiftDate`/`shiftDateTime` — the eight jitter strategies, each with a
  `JitterOptions<T>`-bounded twin (sixteen methods total)**
  - `shiftDate(int days)` — whole-day shift, uniform over `[-days, +days]` (Appendix A.3
    `nextLong(2n+1) - n`), via `LocalDate.plusDays`.
  - `shiftDate(AlterEgo.DateField field)` — `MONTH`: uniform random day within the input's own
    year and month (`nextInt(lengthOfMonth)`, 1-based). `YEAR`: uniform random day within the
    input's own year, leap-aware (`nextInt(lengthOfYear)`, 1-based, via `LocalDate.ofYearDay`).
  - The six `shiftDateTime(...)` overloads: each pairs one of the two date strategies above
    (applied to the date part, drawn first) with one of three time strategies (applied to the
    time part, drawn second):
    - `int seconds` — whole-second shift, uniform over `[-seconds, +seconds]`.
    - `LocalTime start, LocalTime end` — uniform random point in `[start, end]` inclusive, to the
      second (`nextInt(endSecondOfDay - startSecondOfDay + 1)`); `start` after `end` is an
      `AlterEgoConfigException` at call time.
    - `AlterEgo.TimeField.HOUR` — same hour as the input; uniform random minute then second, each
      `nextInt(60)`.
  - Nanoseconds are zeroed in every `shiftDateTime(...)` output, unconditionally, regardless of
    which time strategy ran.
  - The `JitterOptions<T>`-bounded twin of each method applies the clamp last, inclusive, typed to
    the value; values outside the bound are clamped to it, not rejected (spec: "values near a
    bound pile up on it").
  - Equal inputs must jitter identically — this falls out of using `context.random()` normally and
    needs no special-casing, but it's worth a dedicated test given jitter's draw is arithmetic on
    the value itself, not a dictionary pick.
  - Acceptance: uniform-in-range proven over a large sample for every one of the eight strategies
    (including leap-year coverage for `shiftDate(YEAR)`); nanosecond-zeroing proven for every
    `shiftDateTime(...)` overload; `LocalTime start` after `end` rejection test; clamp-bound
    piling proven at the boundary for both `LocalDate` and `LocalDateTime`; determinism test.

- [ ] **3. `emailAddress()`**
  - Split at the **last** `@` (spec section 4.4). No `@` in the input → treat the whole input as
    a bare local part; output gains `@` plus the chosen domain.
  - Local-part replacement is class-wise and in place: each ASCII letter is replaced by a letter
    of the same case, each ASCII digit by a digit, every other character (dots, hyphens, plus
    tags, non-ASCII) is left untouched — same "replace in place, preserve shape" family as
    `mask()`/`pattern()`'s literal-copy behaviour, not a dictionary pick.
  - Domain: RFC 2606 reserved set by default (`example.com`, `.org`, `.net` — confirm the full
    set RFC 2606 actually reserves before hardcoding it, don't rely on the three named in the
    spec's illustrative table alone), with options to preserve the input's own domain or map it
    to a caller-supplied one.
  - Acceptance: last-`@` split test (email with multiple `@`s in the local part, e.g. a quoted
    local part); no-`@`-input test; class-wise replacement test (case preserved, non-alphanumeric
    characters untouched); fictionality property test (every default-configured output's domain
    is in the reserved set, large sample); domain-preserving and domain-mapping option tests.

- [ ] **4. Source and verify the Ofcom drama telephone number ranges — same three-part gate as
  M2's dictionaries, much smaller in volume**
  - This is real external regulatory data (Ofcom's published drama/fiction telephone number
    guidance), not something to type from the spec's illustrative examples (`020 7946 0xxx`,
    `07700 900xxx`, `01632 960xxx`) without independently checking them against Ofcom's own
    current published source — those three are a starting point to verify, not a citation.
  - **Provenance + licensing + data-processing, exactly as required for every dictionary file**:
    record the source (Ofcom's own page/document), the exact URL, retrieval date, and licence
    (most Ofcom regulatory publications are Crown-copyright/OGL — confirm, don't assume) in
    `docs/dictionaries.md` (or a new sibling doc if phone ranges don't fit naturally there —
    decide which, don't silently bolt them onto the dictionaries doc if the shape doesn't fit).
  - Per spec section 9's existing dictionary-resource convention, these "structural rule tables"
    live in the per-country resources alongside the dictionaries (`PLAN.md`'s own words) — design
    the file format (flat list of ranges? range + a display-format template, given real Ofcom
    numbers include a mix of geographic `01`/`02` codes and the `07700 900xxx` mobile range with
    different digit-grouping conventions?) and add it to the same build-time well-formedness
    check family as `DictionaryWellFormedness`, or a sibling class if the shape doesn't fit that
    one cleanly.
  - Acceptance: the three-part gate holds for the range data; a build-time check fails on a
    malformed or unlicensed range file, same discipline as dictionaries.

- [ ] **5. `phoneNumber()`**
  - Digits replaced (in place, punctuation and grouping preserved — same "replace in place"
    family as `emailAddress()`'s local part); by default the *output* lands inside one of the
    ranges from step 4, chosen deterministically like any other built-in pick.
  - `PhoneOptions.realistic()` opts out (matches `PostcodeOptions.realistic()`'s established
    shape from M2 — check `PostcodeOptions` before designing this one).
  - Countries with no defined range fall back to plain in-place digit replacement with **no
    fictionality guarantee** — this must not throw; it's a documented, lesser category, not a
    failure (spec section 4.1). Only `GB` ships a range table in v1; confirm the no-range
    fallback path is actually exercised by a test using an unshipped country, not just asserted
    in prose.
  - Acceptance: fictionality property test (every default-configured GB output falls inside a
    published range, large sample); punctuation/grouping-preservation test; `realistic()`
    opt-out test; no-range-country fallback test (does not throw, produces a digit-replaced
    output, documented as unguaranteed).

- [ ] **6. Milestone test gates**
  - Fictionality property tests for `emailAddress()` and `phoneNumber()` (large samples, per
    spec section 10) alongside the existing `postcode()` one from M2 — consider whether these
    belong in one shared fictionality test class now that there are three, rather than three
    separately-named ones; not required, just worth deciding rather than drifting into it.
  - Golden-output tests for the reference salt across every new M3 built-in (`shiftDate`,
    `shiftDateTime` — a representative selection across the eight strategies, not all sixteen
    methods — `emailAddress`, `phoneNumber`), added to the existing `GoldenOutputsTest`, matching
    the M1/M2 pattern: generated once, eyeballed for plausibility, then frozen.
  - Locale-equivalence test extended to cover `emailAddress()` and `phoneNumber()` (jitter
    built-ins are not country-scoped, so they don't need this — confirm that's actually true
    before skipping them, since it's a real acceptance criterion for every other built-in in this
    project so far).
  - Acceptance: `./gradlew build` green; all M3 "done when" criteria in `PLAN.md` met (jitter
    proven uniform-in-range and deterministic; equal inputs jitter identically; clamps behave at
    the boundaries; nanoseconds zeroed in every `shiftDateTime(...)` output; fictionality
    property tests pass for reserved email domains, drama phone ranges, and impossible postcodes
    carried over from M2).
