# M5 — Record coherence

Ordered checklist; spec references are to `SPECIFICATION.md`. Package root:
`io.github.dconneely.alterego`.

**Design note, decided before implementation started**: `RecordScope.apply(transformation, value)`
takes only a value — `Transformation<T>` is a plain `Function<T, T>` with no scope parameter — so
the active scope has to reach the `TransformationContext` created deep inside
`DefaultTransformation.apply(...)` through a side channel. A `ThreadLocal<DefaultRecordScope>`,
set by `RecordScope.apply(...)` for the duration of the wrapped call and restored in a `finally`
block, is the mechanism: it is exactly as safe as the documented "one thread per scope" rule
already requires, is fully deterministic (never consulted across threads, never time- or
machine-dependent), and needs no change to any already-published public signature. Both
top-level and `derived(...)` contexts created while a scope is active pick up the same active
scope automatically (they consult the same thread-local when `record()` is first called), which
is what gives composites (`fullName()`-style delegation) coherence for free, per the section 2.2
invariant.

**Amendment, made mid-milestone (project owner, 2026-07-26)**: the original design below had only
`city()` setting `UK_POSTCODE_AREA`/`UK_NATION`, with `postcode()`/`phoneNumber()` as pure
consumers — but section 6.2's own illustrative line ("asking for the postcode first ties down the
town") and section 6.3's attribute description ("set by `city()`... or resolved by `postcode()` if
it runs first") both say otherwise. Resolved by adding `RecordAttributes.isActive()` (a fourth,
no-randomness-cost method: true inside a real scope, false outside any) so `postcode()`/
`phoneNumber()` can tell "nothing fixed yet, but a real scope is active" apart from "outside any
scope" — the distinction needed to safely *establish* the place (via `computeIfAbsent`, picking a
real town from the country's dictionary so a later `city()` always matches) only when it's
actually worth it, never spending randomness on it outside a scope where it would silently perturb
every subsequent draw and break output stability. See `PlaceCoherence` (shared by both) and the
updated items 1, 4, 5 below.

- [x] **1. `DefaultRecordScope` + `ScopedRecordAttributes`**
  - `DefaultRecordScope implements RecordScope`: a plain (non-concurrent — single-thread use is
    already a documented precondition) `Map<AttributeKey<?>, Object>`, plus the salt and an
    optional record key (`null` for an anonymous scope). `apply(...)` installs itself on the
    thread-local for the duration of the call, restoring whatever was previously active
    afterward (defensive against accidental re-entrant use, not just the documented case).
    `with(key, value)` pre-seeds via the same `set` logic `RecordAttributes.set` uses. `close()`
    discards the map.
  - `ScopedRecordAttributes implements RecordAttributes`: a thin view over one
    `DefaultRecordScope`, carrying the *asking context's own* `Randomness` for the anonymous-scope
    `computeIfAbsent` fallback (section 6.2: "in an anonymous scope the resolver receives the
    asking strategy's own randomness").
  - `DefaultRecordScope`'s own `set`: first write wins; an equal second write is a no-op; a
    conflicting second write throws `AlterEgoCoherenceException` naming the attribute.
  - `DefaultRecordScope`'s own `computeIfAbsent`: keyed scope (record key present) derives
    `Randomness` via a new `Derivation.recordRandomness(salt, attributeName, recordKey)` (Appendix
    A.1, purpose `alterego/1/record`, counter 0, domain slot = attribute name, canonical slot =
    record key) — independent of which field asks first. Anonymous scope uses the resolver's
    caller-supplied (asking context's) `Randomness` instead.
  - `DefaultTransformationContext.record()` (replacing its current always-`NoOp` stub): consult
    the active thread-local scope; if present, return its `ScopedRecordAttributes` view (lazily,
    same pattern as today); otherwise fall back to `NoOpRecordAttributes` exactly as before.
  - Acceptance: first-touch-wins test; conflicting `set` throws `AlterEgoCoherenceException`
    naming the attribute; equal second `set` is a no-op; keyed-scope `computeIfAbsent` resolves
    the same value regardless of which field calls it first (field-order independence); anonymous
    scope `computeIfAbsent` is first-asker-resolved (documented, not field-order independent);
    outside any scope, behaviour is unchanged (existing `DefaultTransformationContextTest`
    outside-scope tests must still pass untouched).
  - **Amendment**: `RecordAttributes` also has `isActive()`: `false` on `NoOpRecordAttributes`,
    `true` on `ScopedRecordAttributes`. Touches no map, derives no randomness — a plain constant
    per implementation.

- [x] **2. `AlterEgo.record()` / `record(String key)` + `derived(...)` sharing**
  - Replace the `UnsupportedOperationException("M5")` stubs with `new DefaultRecordScope(salt,
    null)` and `new DefaultRecordScope(salt, key)` (key non-null, no charset restriction — it
    feeds the canonical slot of Appendix A.1, which is NUL-safe by construction, not the domain
    slot).
  - No code change needed for `derived(...)` sharing beyond the above — verify (don't just
    assert) that a composite strategy's `derived(...)` child context sees the same scope's
    attributes as its parent, since this falls out of the thread-local design rather than being
    explicitly wired.
  - Acceptance: a two-field record scope test (`rec.apply(t1, ...)` then `rec.apply(t2, ...)`)
    where `t2`'s strategy reads an attribute `t1`'s strategy set; a composite (`fullName()`-style)
    delegation test proving the derived child sees the parent's record attributes.

- [x] **3. Built-in coherence: `city()`**
  - New `CityStrategy` (replacing the generic `NameDictionaryStrategy` currently used for
    `city()`): picks from the town dictionary's entries (not just `values()`, so tags are
    available); if `AlterEgoAttributes.UK_POSTCODE_AREA` is already fixed, restrict the pick to
    town entries tagged with that exact area (falling back to an unconstrained pick if the fixed
    area matches no town — still deterministic, same "consume the same randomness either way"
    pattern as `NameOptions.preserveInitial()`'s fallback; documented as a v1 limitation, not
    silently dropped); otherwise pick freely and `set` both `UK_POSTCODE_AREA` and `UK_NATION`
    from the chosen town's tags.
  - Must be byte-identical to the existing M2 `cityGoldenOutput` outside any scope: same
    `random.pick(...)` call over the same list size/order as today's `values()`-based pick (an
    `entries()`-based pick over the same underlying parsed rows, in the same order, is
    index-for-index identical) — the `set(...)` calls that follow consume no randomness, so
    outside a scope (where `set` is a no-op) output is unaffected either way.
  - Acceptance: golden-output regression test (M2's existing value, untouched); area-consistency
    test (`city()` run second in a scope with a fixed area picks a matching town); nation-implied
    test; fixed-but-unmatched-area fallback test (deterministic, doesn't throw).

- [x] **4. Built-in coherence: `postcode()`**
  - When `UK_POSTCODE_AREA` is fixed, build the outward code from that literal area string plus a
    freshly-drawn 1 or 2 trailing digits (still a uniform choice between the two valid shapes for
    that area's own letter-length); the inward code's generation is untouched either way (impossible
    letter rule unaffected, per spec 6.3). This is an *additional* branch alongside the existing
    unconstrained outward-code generation — the unconstrained path's own code must not change at
    all, or M2's `postcodeGoldenOutput` breaks.
  - **Amendment**: when `context.record().isActive()` (a real scope, whether or not the area is
    fixed yet), the area used is `PlaceCoherence.establish(context, country)` — which returns the
    already-fixed area unchanged (via `computeIfAbsent`'s own early-return, no extra randomness
    spent) if one exists, or, if `postcode()` is the first field to touch the record's place,
    picks a real town from the country's dictionary and fixes both `UK_POSTCODE_AREA` and
    `UK_NATION` from it before returning the area. Outside any scope (`isActive() == false`), the
    original unconstrained `outwardCode(random)` path runs, completely untouched.
  - Acceptance: golden-output regression test (M2's existing value, untouched); area-consistency
    test (postcode's outward code starts with the fixed area, in a scope where `city()` ran
    first); **postcode-first test** (postcode runs first in a fresh scope, then `city()` in the
    same scope always finds a matching town — proving establishment, not just consumption);
    impossible-inward-code guarantee still holds inside a scope (fictionality property test,
    in-scope variant).

- [x] **5. Built-in coherence: `phoneNumber()`**
  - Re-tag `dictionaries/GB/phone-ranges.txt`: a second tag per row, the associated postcode area
    for geographic ranges (cross-checked against `towns.txt`'s own area strings — Leeds→LS,
    Sheffield→S, Nottingham→NG, Leicester→LE, Bristol→BS, Birmingham→B, Edinburgh→EH, Glasgow→G,
    Liverpool→L, Manchester→M, Newcastle/Tyneside→NE, Cardiff→CF, Northern Ireland→BT, London→one
    row per postcode area exactly as `towns.txt` already lists them: E, EC, N, NW, SE, SW, W, WC —
    same "list once per area" precedent as `towns.txt`'s own London rows, same well-formedness
    rule: not a duplicate row since the (value, tags) pair differs per area); `NONE` for the
    01632 no-area range (the designated geography-neutral fallback); `MOBILE` for the mobile
    range (never a match target and never the neutral fallback — reachable only via the
    unconstrained "no area fixed" pool, same as before M5). Reading (RG) has no matching town in
    `towns.txt` — documented, not a bug: still reachable via an explicit `.with(UK_POSTCODE_AREA,
    "RG")` pre-seed.
  - `DictionaryWellFormedness.validatePhoneRangeTags`: now 2 tags per entry (template, area);
    validate the area tag is `NONE`, `MOBILE`, or 1–2 uppercase letters.
  - `PhoneNumberStrategy`: same `isActive()` + `PlaceCoherence.establish(...)` amendment as
    `postcode()` — the resolved area (fixed or freshly established) picks the matching range,
    falling back to `NONE` (01632) if none matches, never `MOBILE`. Outside any scope, the
    unchanged M3 unconstrained pick over every distinct shipped range (`docs/phone-ranges.md`'s
    17 — `distinct()` on template, since London's range now appears on 8 tagged rows for
    area-matching, and the unconstrained pool must not shift size purely from that).
  - Acceptance: golden-output regression test (M3's existing values, untouched); place-matching
    test (`phoneNumber()` after `city()` picks London gets a `020 7946 0xxx` number); **phone-first
    test** (phone runs first in a fresh scope, `city()` afterward always finds a matching town);
    neutral fallback test (a fixed area with no phone range, e.g. Bradford's `BD`, falls back to
    `01632 960xxx`, not to some other geographic range); fictionality property test still holds
    for every in-scope output too.

  - The full spec section 10 record-coherence suite: town/postcode/phone agree whichever field
    runs first (test all three orderings, not just city-first); keyed scopes are field-order
    independent for resolved attributes (a `computeIfAbsent`-based custom attribute, not just the
    built-ins); two scopes never share state (two `RecordScope` instances, same `AlterEgo`
    instance, independent attribute maps); outside-scope outputs byte-identical to pre-M5 golden
    outputs (rerun `GoldenOutputsTest` unchanged — no new golden values needed, since nothing
    outside a scope should differ); conflicting `set` throws `AlterEgoCoherenceException`; a
    custom Companies House-style strategy coheres via `UK_NATION` (spec section 7's own example:
    `SC...`/`NI...` prefix, or no prefix for England/Wales).
  - Fictionality property tests (postcode inward code, email domain, phone range) still pass
    *inside* a scope, not just outside one — a scope changes which range/outward-shape is picked,
    never removes the fictionality guarantee itself.
  - Acceptance: `./gradlew build` green; all M5 "done when" criteria in `PLAN.md` met.
