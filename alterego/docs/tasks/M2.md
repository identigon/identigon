# M2 — Dictionaries + name/organisation/address strategies

Ordered checklist; spec references are to `SPECIFICATION.md`. Sourcing decisions for every
dictionary category are already made and recorded in `docs/dictionaries.md` — this milestone is
about building the infrastructure, curating the actual data from those decided sources, and
implementing the strategies that consume it.

**Independent review gate, same discipline as M1's conformance vectors**: the sourcing
*decision* for each category is already independently approved (`docs/dictionaries.md`), but the
curated *content* — which actual names/streets/towns end up in the committed `.txt` files, and
the postcode-area/nation tags on each town — is not. Machine-extracted candidate dictionaries are
draft until independently reviewed: a representative sample confirmed plausible and correctly
tagged by someone other than whatever generated the candidates. Do not mark this milestone's
dictionary-content step done without that confirmation.

- [x] **1. Dictionary resource format + loader**
  - File format (spec section 9): UTF-8, `dictionaries/<country>/<name>.txt`, one entry per
    line, optional tab-separated tag fields (e.g. town → postcode area, nation), plus the
    provenance header block (source, exact data URL, licence name + URL, retrieval date,
    licence-name reference into `dictionaries/LICENCES/`).
  - Loader: caches parsed dictionaries per (country, name); resolves by locale's country only —
    exact `Locale` country match, else `AlterEgoConfigException` naming the country and the
    dictionary that was missing (section 4 lookup rule — no language fallback, no silent borrow
    from another country).
  - Build-time well-formedness check (a Gradle task or a test that fails the build): every
    shipped dictionary is non-empty, deduplicated, sorted, has a provenance header, and its
    cited licence name matches a file under `dictionaries/LICENCES/`. Town-file tag fields
    validate against the known postcode-area and `UkNation` sets.
  - Test against small synthetic fixture dictionaries committed under test resources — do not
    wait for real data to test the loader's mechanics.
  - Acceptance: loader unit tests green against synthetic fixtures; a deliberately malformed
    fixture (missing header, bad tag, duplicate entry) fails the well-formedness check with a
    clear message.

- [x] **2. Curate real dictionary data** (see the independent review gate above) — **5 of 5
  dictionaries generated via `tools/curate_dictionaries.py` and committed under
  `src/main/resources/dictionaries/GB/`: surnames, first-names, towns, street-themes,
  street-types, organisation-components. Review: all 6 files confirmed — frozen content.**
  - Current scope per category (`docs/dictionaries.md` is authoritative if this drifts):
    surnames — all four UK nations, each sized to its real population share (ONS England &
    Wales top-20 for two cohort years, 2024 and 2014; NRS Scotland's top-10 for 2025);
    first names — the same population-sized approach, ONS England & Wales top-20 boys + top-20
    girls for two cohort years 29 years apart (2025, 1996), plus NRS Scotland and NISRA Northern
    Ireland top-10 boys + top-10 girls each for the current year; towns/cities — a curated
    top-20 UK-wide (all four nations, since ISO "GB" covers the whole UK) population ranking
    with postcode-area + nation tags; street names — a compositional theme-word/type-word pair;
    organisation-name components — IPO trade mark owner names mined for common word tokens.
  - **Every reduction/extraction step must be a repeatable, documented, scripted process — not
    manual transcription from a report into a file.** Write a script (e.g.
    `tools/curate_dictionaries.py`, matching `tools/verify_vectors.py`'s standing) that takes
    the raw downloaded source files (cached locally under `tools/data-cache/`, see
    `tools/data-cache/SOURCES.md`, so re-running doesn't depend on source pages staying up or
    unchanged — or their small direct-download URLs, for the sources not yet cached, e.g. both
    IPO ZIPs, confirmed directly fetchable without an account) and deterministically produces
    each dictionary `.txt` file: sorted, deduplicated, correctly tagged, with its provenance
    header. State the exact processing rule in the script's own documentation (e.g. "top 20 by
    population, ties broken by X"; "top 20 boys + top 20 girls per cohort year, deduplicated,
    re-sorted") so it can be re-run and audited, not just trusted once.
  - Write the provenance header for each resulting `.txt` file from the confirmed details
    already in `docs/dictionaries.md` — do not re-derive or guess at licence text.
  - Organisation-name components: mine common word tokens from IPO owner names — commit only
    the derived word list, never raw owner-name records.
  - **Choose a representative sample of each curated file for independent review before treating it
    as final.** Note any judgement calls made during extraction so the reviewer can
    assess them.
  - **The three-part gate applies to every single dictionary file individually, no exceptions**
    — not satisfied by having each piece present *somewhere* across the project:
    1. **Provenance**: organisation/dataset name, exact original data URL, retrieval date, in
       the file's own header (spec section 9).
    2. **Licensing**: licence name in the header matches a committed file under
       `dictionaries/LICENCES/` with the licence's exact URL and full text — not "this is
       probably fine," an actual checked and cited licence (`docs/dictionaries.md`'s sourcing
       policy). This includes word lists with no copyright concern (e.g. composed street-name
       vocabulary): the requirement there is accuracy/reproducibility, not redistribution
       rights — general-knowledge words still need a real citable source, not something typed
       from memory, because memory can be subtly wrong with no way to check.
    3. **Data processing**: the exact reduction/curation rule stated and scripted (see above),
       not manual transcription.
    A dictionary missing any one of the three is not done, regardless of how solid the other
    two are.
  - Acceptance: the three-part gate holds for every dictionary file; reviewer confirms each
    curated dictionary is plausible and correctly tagged; the curation script exists and
    re-running it reproduces the same committed files; only then are the files treated as
    frozen content for the milestone's remaining steps.

- [x] **4. `firstName()`, `lastName()`, `fullName()`**
  - `firstName()`, `lastName()` draw from the dictionary; `NameOptions.preserveInitial()`
    with the no-matching-initial fallback (unconstrained pick, deterministic — spec section 4.2).
  - `fullName()` implements the pinned tokenisation rules exactly (trim, whitespace-split,
    first/last/middle-token domain assignment, hyphenated-token splitting, blank-input passthrough,
    untokenisable-input surname fallback) and cross-checks against standalone `firstName()`/
    `lastName()` via `context.derived(...)`.
  - Acceptance: cross-consistency test (`fullName("Alice Smith")` parts equal `firstName("Alice")`
    / `lastName("Smith")`); tokenisation tests cover middle names, hyphens, single tokens, blank
    input; `en-GB`/`cy-GB` locale-equivalence test passes (country-scoped resolution, section 4).

- [x] **5. `city()`, `streetAddress()`, `postcode()`, `organisationName()`**
  - `city()`: draws from the town dictionary (reuses `NameDictionaryStrategy`, unconstrained
    pick); carries postcode-area/nation tags for later record-coherence use in M5 (not read
    here — just not lost, since the strategy only touches `dictionary.values()`).
  - `streetAddress()`: house number 1–299 (deterministic draw) + a complete entry from the
    street dictionary (`StreetAddressStrategy`).
  - `postcode()`: UK format with the impossible-inward-code fictionality guarantee (section
    4.1: inward code ends in `C I K M O V` by default; `PostcodeOptions.realistic()` opts out,
    drawing from the full alphabet instead). `PostcodeStrategy` generates a plausible outward
    code (one of the common shapes `A9`/`A99`/`AA9`/`AA99`) — the rarer trailing-district-letter
    shapes (`W1A`) and coupling the outward code to a real postcode area are both out of scope
    for v1 (the latter is M5's record-coherence job, spec section 6.3), documented as a known
    limitation in `PostcodeStrategy`'s Javadoc, not silently dropped.
  - `organisationName()`: composed from the tagged (`MODIFIER`/`NOUN`) organisation-component
    dictionary via `OrganisationNameStrategy` (3 distinct words: `[MODIFIER-or-NOUN] + NOUN +
    NOUN` — see `docs/dictionaries.md`, "Organisation-name components", for the full
    generation-algorithm reasoning); preserves a recognised legal suffix if present in the
    input (case-insensitive detection, canonical casing on output), including the Welsh forms
    (`LegalSuffixes`, a fixed per-country list, not a downloaded dataset).
  - Factory methods fail fast (`AlterEgoConfigException`) when the locale has no country or the
    country has no resources for that dictionary/format — verified for all four built-ins
    against both a country-less locale and an unshipped country (`Locale.US`).
  - Acceptance: fictionality property test (every postcode violates the inward-code rule,
    large sample — `PostcodeTest.everyDefaultOutputViolatesTheInwardCodeRule`, 500-sample loop)
    passes; factory methods fail fast on missing locale/country (all four built-ins); non-ASCII
    and empty-string inputs covered for every built-in in this step
    (`nonAsciiAndEmptyInputsAreHandled` in each test class). Real dictionary examples
    eyeballed for plausibility (e.g. "12 Springfield Orchard, Nottingham, K1 4CO";
    "Trading Capital Centre Ltd").
